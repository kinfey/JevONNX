# 从“会聊天”到“会决策”：用 Microsoft Olive 与 ONNX 把 SLM 放进行为逻辑

> 从自动化点餐的一次追问出发，探索 Jev 式结构化决策如何走向端侧，再用 Qwen3.5-0.8B 的微调实践搭起通往垂直行业的桥。

## 1. Jev 的意义：让系统更快决定下一步，而不只是更会说话

沿着此前讨论过的自动化点餐场景，我们先想象这样一个时刻。

顾客说：“来一份套餐，饮料不要太甜。”

对话模型可以立即给出一句自然的回复。但对于点餐系统，真正的问题才刚刚开始：套餐是否已经确定？“不要太甜”能否直接映射为某个甜度？当前菜单是否支持这种调整？下一步应该追问、修改购物车，还是交给确认环节？

**系统需要的不是再多一段解释，而是一个能够推进流程的判断。**

传统规则擅长处理明确条件：商品售罄就不可下单，订单提交前必须确认，支付操作必须授权。这些规则不应该被模型取代。然而，当输入开始包含模糊表达、上下文和用户偏好，规则树就会不断长出分支。另一种极端是让大模型接管所有判断，但每一次简单分流都经历完整的推理和生成，又可能让业务流程背上不必要的等待。

这正是我理解的 Jev 的意义：**把语义理解转化为结构化的行为判断，缩短从“听懂”到“执行”的距离。**

例如，应用可以把一次点餐对话拆成几个有限问题：

| 决策问题 | 输出形式 | 如何推动流程 |
|---|---|---|
| 关键偏好是否仍然不明确？ | `noul`：布尔问题的概率 | 决定是否追问 |
| 下一步进入哪个环节？ | `choice`：候选动作及分布 | 路由到澄清、购物车或确认 |
| 需要人工介入的程度如何？ | `score`：有序等级的期望值 | 决定是否升级处理 |

这些输出不是执行权限。模型可以建议“进入确认环节”，但不能因此绕过库存校验、过敏原规则或支付授权。应用仍然需要显式的状态机、约束和工具调用边界。

此前对点餐场景的探索给我的启发是：**结构化框架的价值，不只是让输出容易解析，而是让智能体少走一些不必要的决策步骤。** 当问题、候选项和执行边界提前定义好，模型不必每次都重新发明工作流。

本文沿用这一思路，但需要先划清边界：下面的微调不是训练 Jev 官方模型，也不是复现它的私有实现。我们借鉴 Jev 式 typed decisions 的接口思想，参考开源 [Hmm](https://huggingface.co/n4ze3m/Qwen3.5-4B-Hmm) 的提示格式，用自己的小模型探索一个可部署的决策组件。

## 2. 端侧 SLM 的落地场景：让判断靠近动作发生的地方

超越基础规则之后，我更关注的价值来自垂直行业：模型能否在动作发生的地方，及时完成一次语义判断？

SLM，即小语言模型，并不天然等于端侧模型。模型规模、上下文长度、运行时、内存和硬件共同决定它能否在目标设备上工作。但相较于把所有判断都送到远端大模型，小模型提供了一种值得探索的分工方式：

**让大模型处理开放问题，让小模型处理高频、边界清晰的语义决策，让确定性代码负责约束与执行。**

### 从餐厅终端到具身智能

在点餐终端，端侧小模型可以判断用户是否表达了修改意图、当前信息是否充分，以及应该唤起哪一个业务模块。即使网络波动，某些本地判断也不必随之中断；敏感上下文还可以减少不必要的外传。当然，这需要整个应用的数据流也支持本地处理，而不是只把模型文件放在设备上。

把这个思路迁移到具身智能，问题会变得更加直接：“用户是在要求机器人靠近，还是只是描述位置？”“当前任务应该继续，还是等待澄清？”这些语义判断可以靠近设备运行。

但这里必须区分两个层次：语言模型可以参与任务级意图判断，却不应承担碰撞避免、急停或底层运动控制的唯一责任。毫秒级响应是值得追求的工程目标，不是模型小、或者导出成 ONNX 后自动得到的承诺。真正需要测量的是目标设备上包含输入处理、模型推理、策略判断和工具执行的端到端延迟。

### 从单个助手到多智能体编排

另一个方向是多智能体系统。复杂请求可能需要研究、计划、执行和验证等不同角色，但不是每一次角色切换都需要一轮开放式讨论。

一个本地决策组件可以回答：

- 当前请求应交给哪个智能体？
- 执行所需的信息是否齐全？
- 工具结果是否需要进入复核环节？
- 当前状态应该继续、重试，还是交由人处理？

我目前关注的方向，是通过托管智能体承担长流程编排，再结合受约束的自主执行能力；小模型则可以成为其中高频、局部的判断节点。这里的“自主”并不意味着无限授权，工具权限、超时、重试预算和人工审批仍然属于系统设计。

这也为 ONNX 提供了很好的发挥空间：把经过训练的判断能力打包为可由运行时加载的部署产物，让模型更容易进入应用工程，而不必让每个终端都承担完整的训练工具链。

不过，**ONNX 是部署路径，不是跨硬件性能的保证书**。本次工作流输出的是 CUDA FP16 模型。要迁移到 CPU、移动设备或 NPU，还需要匹配的执行提供程序、算子支持，以及可能的重新导出、量化和回归评估。

## 3. 先微调一个通用决策组件，再走向垂直领域

为了验证这条路径，我没有直接从一个复杂行业系统开始，而是先做通用 typed decisions 实验：

**Qwen3.5-0.8B → Olive LoRA 微调 → Olive ModelBuilder 导出 → ONNX 概率测试 → Hugging Face 发布流程。**

对应的实现位于 [Qwen3_5_0.8B_FT.ipynb](../Qwen3_5_0.8B_FT.ipynb)。它的意义不是用一个 notebook 证明某个行业已经被解决，而是把“数据如何变成可部署判断能力”的链路具体化。

### 第一站：训练的对象不是长篇回答，而是有限选项

基础模型选择 [Qwen/Qwen3.5-0.8B](https://huggingface.co/Qwen/Qwen3.5-0.8B)，数据来自 [n4ze3m/typed-decisions-synth](https://huggingface.co/datasets/n4ze3m/typed-decisions-synth)。

数据里的一个 state 可以对应多个问题。预处理把每个问题展开为一条训练样本，保留原始 case-level train/validation 划分，避免同一个 state 的不同问题泄漏到训练集和验证集两侧。

问题被统一为候选字母。例如：

```text
State (data to evaluate):
Help! My payouts have failed for 3 days. I need the money today.

Question:
Which team should handle this?

Options:
A: billing — Payments, invoicing, refunds
B: technical — Bugs, outages, integrations
C: sales — Pricing, upgrades, new accounts
Return only the option letter.
```

`choice` 对应分类选项；`noul` 使用 `false / true`；`score` 使用由低到高的等级。训练时，choice 选项按 state 和问题 ID 做确定性打乱，降低固定字母位置带来的偏差；score 的等级顺序和 noul 的布尔顺序则保留。

这里还有几个看似细小、实际上决定一致性的选择：使用同一 chat template，关闭 thinking，检查训练文本是否确实以推理 prompt 为前缀，检查选项字母是否为单 token，以及丢弃超过 768 token 的样本，而不是盲目截断。

这些处理不是给数据“做美容”，而是在定义模型与应用之间的协议。

### 第二站：用 Olive 把实验配置变成可检查的工作流

这次使用 Microsoft Olive 从固定源码 revision 构建 wheel，并先通过 `olive finetune --dry_run` 生成版本匹配的配置，再调整数据预处理和验证逻辑。

主要配置如下：

| 项目 | 本次 notebook 配置 |
|---|---|
| 微调方式 | LoRA，rank 32，alpha 64 |
| 目标模块 | `q_proj/k_proj/v_proj/o_proj` 与 `gate_proj/up_proj/down_proj` |
| 学习率与 epoch | `1e-4`，1 epoch |
| 序列长度 | 768 |
| 每设备 batch / 梯度累积 | 1 / 16 |
| 训练 / 导出精度 | BF16 / FP16 |
| 数据预处理 | `line-by-line`，每个问题一个序列 |

把默认 JOIN 改成逐行样本，是为了不把独立问答无意地拼接成连续语料。正式训练前使用 `RunConfig.model_validate(...)` 检查配置；执行时使用 Olive Python API，让异常留在 notebook 中，而不是只看到一层 `CalledProcessError`。

**这里不能忽略一个重要差异：本次 Olive 工作流采用完整问答序列的标准语言模型 SFT，不是 Hmm 的候选字母 hard-label / teacher soft-label 混合目标。** 数据中的 teacher 概率仅保留用于分析，没有进入本次训练损失。因此，不能把 Hmm 的准确率或概率校准效果迁移为这个 0.8B 模型的成绩。

### 第三站：导出模型，也导出完整的运行契约

LoRA adapter 不是终点。部署还需要基础模型、adapter、tokenizer、模型配置和运行时对齐。

Notebook 通过 Olive `ModelBuilder` 将基础模型与 adapter 导出为 CUDA FP16 ONNX。产物不只是一个 `.onnx` 文件，还包括外部权重、tokenizer 资源和 `genai_config.json`。消费者应加载整个模型目录。

这段过程最有教育意义的部分，恰恰是那些版本边界：

| 遇到的边界 | 本次处理思路 |
|---|---|
| 不需要的旧 TorchAO 与 Transformers 冲突 | 标准 BF16 LoRA 不依赖它，在安装流程末尾移除 |
| Qwen3.5 内核退回参考实现 | 安装并检查 causal-conv1d 与 Flash Linear Attention |
| 公共模型导出仍要求 HF token | 显式设置匿名读取 |
| Qwen3.5 的 EOS 配置位于 `text_config` | 在本地导出副本中补齐顶层配置 |
| 更新后的 CUDA 包与当前运行环境不匹配 | 固定 notebook 使用的 ORT GPU 1.26.0 / GenAI CUDA 0.14.0 组合 |
| Olive revision 与旧 GenAI Builder API 不一致 | 为当前 FP16 导出路径加入版本限定的兼容处理 |
| 文本模型被按多模态 decoder 导出 | 设置 `exclude_embeds=False`，保留 token embedding |

这些是本次环境的处理记录，不是适用于所有版本的通用补丁。尤其是版本兼容代码，应当被视为技术债：升级时重新检查接口和输出，而不是永久复制。

这次经历也提醒我，锁定 Olive commit 还不等于完整可复现。后续仍应记录基础模型与数据集 revision、完整依赖版本、GPU/驱动信息和最终发布 commit。

### 第四站：让测试回答两个不同的问题

第一个问题是：**模型能不能运行？**

独立的 [Python 测试脚本](../test_qwen35_onnx.py) 加载导出目录，读取 validation 样本，执行生成并解析候选字母。这是 smoke test，用于检查模型、tokenizer 和生成循环能否协同工作，不是质量评估的终点。

第二个问题是：**这个判断能不能被业务使用？**

参考 Hmm 的方式，新增的 ONNX cell 不依赖自由生成的解释，而是在 prompt 后读取第一个生成位置的 logits，只保留有效选项对应的字母，再做 softmax：

```python
# candidate_logits 只包含当前问题有效选项的首 token logits
shifted = candidate_logits - candidate_logits.max()
probabilities = np.exp(shifted)
probabilities /= probabilities.sum()
```

假设候选为 A、B、C，这个分布表达的是“在这三个候选之间如何分配概率”，并不证明候选集合完整，也不是模型对所有可能答案的绝对可信度。

应用再根据类型解释它：noul 读取 `P(true)`；choice 选择最大概率对应的选项；score 对有序等级计算期望值。示例中的 confidence 使用 `(n × p_max - 1) / (n - 1)`，衡量分布有多集中，**不等于经过校准的正确率**。

因此，我会把完整验证拆开看：accuracy、候选 NLL、ECE 反映判断质量；目标设备上的 P50/P95 延迟、峰值内存、回退比例和任务完成率反映系统价值。当前 notebook 的全验证集指标 cell 使用的是 PyTorch/PEFT 路径；ONNX cell 是示例概率测试，不能把前者直接当成后者的评测报告。还需要比较导出前后的候选分布和实际决策。

本文不提供未经记录的耗时、准确率提升或“已实现毫秒级端侧响应”结论。

### 第五站：发布只是开始，行业闭环才是目的

Notebook 已配置向 [`lokinfey/Qwen3_5_0.8B_jev`](https://huggingface.co/lokinfey/Qwen3_5_0.8B_jev) 上传 ONNX 目录和 Model Card 的流程。这里的链接是发布目标，并不代表本文核验了远端上传状态。

Model Card 应说明基础模型、训练数据、损失函数差异、运行时版本、适用范围和未完成的评测。登录使用交互式 token 输入，不把密钥写入代码或提交记录。

通用实验搭好之后，才是垂直化最重要的一步。回到点餐场景，我们需要用真实业务定义状态和动作：菜单版本、购物车、修改记录、明确缺失的信息、哪些情况必须追问，以及哪些动作永远需要用户确认。

行业数据也应围绕这些边界构建，并按会话或业务实体拆分验证集。低置信度、分布外输入、规则冲突都需要拒答或升级路径。模型的任务不是给每个请求硬选一个答案，而是在明确边界内帮助系统更稳妥地前进。

## 4. 总结：小模型的机会，不是缩小聊天框，而是缩短决策链

从点餐的一次追问，到机器人任务级意图理解，再到多智能体的局部路由，它们共享一个问题：系统已经拥有工具，但还需要知道什么时候调用、交给谁，以及什么时候停下来。

Jev 式结构化决策提供了一种接口视角，SLM 提供了把部分语义判断放到本地的可能，Microsoft Olive 把微调与导出组织成工作流，ONNX Runtime 则为部署提供执行路径。

这几者组合起来，真正值得探索的不是“更小的聊天机器人”，而是**能被测量、受约束、可替换的决策组件**。

我希望继续验证的方向，是让托管智能体负责长流程协调，让端侧小模型承担高频局部判断，让确定性代码守住业务与安全边界。判断是否成功的标准，也应该从“回复听起来是否聪明”，转向“系统能否更快、更稳妥地完成正确动作”。

这，才是从会聊天走向会决策的下一步。
